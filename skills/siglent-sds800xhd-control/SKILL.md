# Siglent SDS800X HD Control

Use this skill whenever an AI needs to operate an SDS800X HD series oscilloscope, capture a stopped frame, download waveform data, decode it, or diagnose a mismatch between screen record length and downloaded files. The series shares one platform and command set; every behavior here was verified on an SDS824X HD. Capabilities that depend on channel count, bandwidth, or memory depth (2 vs 4 channels, 50 vs 100 Mpts) must be confirmed against the connected model.

## Non-negotiable Safety Rules

- Never send `ARM`. `TRMD SINGLE` is the only accepted single-shot start operation on firmware `4.8.12.1.1.6.5`. `TRMD` is a firmware-verified short form; the manual's documented spelling is `:TRIGger:MODE SINGle`, which is the same operation (manual printed pp. 243-244). The manual contains no `ARM` command at all, and the target firmware rejected it; both facts stay, but attribute them correctly.
- Configure the trigger only with commands whose result can be read back: `:TRIGger:TYPE`, `:TRIGger:EDGE:SOURce`, `:TRIGger:EDGE:SLOPe`, `:TRIGger:EDGE:LEVel` (manual printed pp. 249-251). Do **not** use the handover block `TRSE EDGE,SR,C1,HT,OFF` / `C1:TRSL POS` / `C1:TRLV 2.5`: `HT` is defined nowhere in the 495-page programming guide, and no per-channel trigger slope or level command exists, so that block asserts a rising-versus-falling decision it can never prove. `:TRIGger:EDGE:SLOPe?` is the only documented statement of slope; a capture whose slope was never read back must not claim a trigger direction. The trigger block is recorded in `manifest.pre_capture_snapshot.trigger`, not implied by the acquisition state.
- A valid capture requires the observed state transition `Ready -> Stop`. A `Stop` observed without a prior `Ready` is not proof of a new capture.
- Roll mode (`:ACQuire:MODE ROLL`) never reports `Ready`; it is a streaming display, not a capture path. Leave it with `:ACQuire:MODE YT` before arming, and never treat `Roll` as `Ready` or as a `Stop` precursor.
- After `Stop`, do not send `STOP`, `ARM`, `RUN`, `TRMD`, trigger/timebase/channel configuration, `WFSU`, or a TCP reconnect while reading the frame.
- In an immutable legacy read, issue every channel's `WF? DAT2` first. Only after all payloads are saved may the caller explicitly issue `WF? DESC`.
- Keep `immutable_capture` and `configured_capture` explicit. Never silently send `WFSU`, restore `TRMD`, or clean up the instrument.
- Never use `max_points` as evidence of instrument record length. It is only a local CSV/downsampling setting.
- Preserve raw payloads and metadata before producing CSV. A short payload is `INCOMPLETE` or `INVALID`, never complete.
- **Silence is the normal outcome of a rejected write.** After every configuration write, read the value back and compare it with the request, and drain `SYSTem:ERRor?` in a loop until it answers `0,"No error"` (the command is undocumented but firmware-verified). A read-back that still holds the old value is a hard failure to diagnose, never a reason to retry a different spelling. `references/command-reference.md` → *Write-Failure Modes* lists every reproduced silent-failure case with its detector.
- **A setting that "will not take" is usually inapplicable, not broken.** Acquisition-context writes (`:ACQuire:SRATe`, `:ACQuire:MDEPth`, `:AcQuire:MMANagement`) are silently discarded while `SAST?` is `Stop`; return to run state before writing them. `TIM:SCAL` is silently clamped by the conservation law `TDIV_max = ACQ:POIN? / (SARA * 10)`, so lower the sample rate **before** raising the timebase. Neither case queues an error, and neither is a frozen or locked instrument.
- **Send one command per `write()`.** Only the first command of a pipelined TCP batch reliably executes: `TRSE` as line 2 or later of one batch is reproducibly rejected with `-113,"Undefined header"`, while the same command alone or first is accepted. `\n`-separated batches and `;` compounds both lose the tail. The bundled `scope_protocol.py` already writes one command per `sendall`; a hand-rolled socket does not inherit that protection.
- **Never invent a query spelling.** An undefined-header *query* returns no bytes at all yet still queues `-113`, so every later `readline()` is short by one response. The resulting cascade of timeouts is off-by-one response skew, not a dead instrument — re-read `*IDN?`, and open a new session to recover instead of concluding the scope needs a reset.

The fallback command index is not a starting point: use it only after the matching task reference and the bundled scripts fail to answer the command question. It indexes only the commands this Skill already records; anything missing from it must be verified against the programming guide and labelled `documented` before use, and the safety rules above always take precedence.

Every setting has both a read and a write form, **except where it does not**: `SARA` / `:ACQuire:SRATe?` reads the rate but `SARA <value>` is rejected `-113` — the write spellings are `:ACQuire:SRATe` and `ACQ:SRAT`. Do not assume symmetry for a short form you have not written before. Reads are the default and are safe at any time; writes change the acquisition context, so they belong before `TRMD SINGLE` and never during a stopped-frame read. The most often missed writes are `:ACQuire:MMANagement`/`:ACQuire:SRATe` (sample rate only applies in `FSRate` mode), `:TRIGger:TYPE` (runt/pulse/serial triggering), `:SEARch` and `:MTESt` enable, `:MEASure:SIMPle:ITEM`, and `:FORMat:DATA` (default precision is only 3 significant digits).

Start with the matching reference's read-only snapshot. Use a setup/enable command only when that workflow requires it and the caller authorized changing scope state. Each reference distinguishes target-hardware-tested behavior from manual-documented behavior and notes feature prerequisites.

**When a setting does not take effect, the next step is a read, not another write.** Read the value back, drain `SYSTem:ERRor?`, and if either disagrees with the request, load [Command reference](references/command-reference.md) → *Write-Failure Modes* before touching the command spelling again. Two of the documented causes (acquisition context written while `Stop`, an over-limit `TIMebase:SCALe`) produce no error at all, and neither is a locked instrument — do not "recover" by resetting the scope, reconnecting, or retrying a variant spelling, because each of those destroys the evidence that would identify the real cause.

## Raw TCP Session

1. Connect once to SCPI TCP port `5025`; do not use legacy shell port `5024`.
2. Send `*IDN?` and save the returned identity before issuing model-specific commands.
3. Use `scripts/scope_protocol.py` for byte-preserving raw TCP queries and IEEE 488.2 blocks; use `scripts/capture_scope.py` for complete segmented waveform downloads, and `scripts/screenshot_capture.py` for a screenshot. `:PRINt?` screenshots are the exception — raw PNG stream, no block header (see Binary Response Rules).
4. Apply channel or acquisition configuration only when explicitly requested, and do it before starting a new single acquisition.
5. Start a single acquisition with `TRMD SINGLE`; never send `ARM`. Poll `SAST?` until `Ready`, stimulate the DUT, then poll until `Stop`. Do not automatically retry.
6. Keep the same socket session for the complete capture. Do not trigger and then reconnect to read the frame.
7. Treat an export as unverified unless raw payload length and descriptor point count agree. A CSV or downsampled view alone does not prove a complete capture.

## Hardware Profile

- Supported series: `SDS800X HD` — SDS802X HD, SDS804X HD, SDS812X HD, SDS814X HD, SDS822X HD, SDS824X HD (2- or 4-channel, 70/100/200 MHz, 50 or 100 Mpts).
- Verified target: `Siglent SDS824X HD`, IP `192.168.10.2`, SCPI TCP `5025`, firmware `4.8.12.1.1.6.5`.
- Port `5024` is a legacy shell-like channel. It may begin with `Welcome to the SCPI instrument 'Siglent SDS824X HD'` and `>>`; never parse either as a query result.
- Channel mapping: `C1=ENABLE`, `C2=nFAULT`, `C3=HOC`, `C4=P4.1/CMP`. This is the bench that was verified, not a default; the scope has no channel-name readback.
- Typical setup: C1/C2/C4 `VDIV 2`, C3 `VDIV 5`, all `OFST 0`, probe `10`; edge trigger on C1 rising at `2.5 V`; `TRMD SINGLE`; `500 ms/div`; `5.00 MSa/s`; `25.0 Mpts`; about `-2 s` trigger delay.
- Expected record: `25,000,000` points, `200 ns` per point, `5 s`.
- Sample rate is only directly settable in `:ACQuire:MMANagement FSRate` mode, and only while the scope is not `Stop`; the typical setup above observed `5.00 MSa/s` in the default management mode, which derives it from the timebase. Apply the acquisition context in the order `:ACQuire:MMANagement` → `:ACQuire:MDEPth` → `:ACQuire:SRATe` → `:TIMebase:SCALe` → `:TIMebase:DELay`; the reverse order cannot reach a long timebase because `TDIV_max = ACQ:POIN? / (SARA * 10)`.
- Front-panel lock is the explicit `:SYSTem:REMote ON|OFF` state (manual printed p. 264), not a side effect of opening a TCP session.

## Approved Workflows

### New Capture

1. Connect once and identify the scope.
2. Snapshot configuration before changing anything.
3. If requested, configure channels and trigger before starting acquisition.
4. Issue `TRMD SINGLE`; never issue `ARM`.
5. Poll `SAST?` until `Ready`; stimulate the DUT; poll until `Stop`.
6. Freeze the command set. Do not restore `TRMD AUTO` automatically.
7. For a full-length transfer, use the modern segmented path with the bundled script. Treat it as `configured_capture` because the scope receives transfer-selection writes after `Stop`; the path is verified for complete transfer integrity, but it is not called immutable:
   - `WAV:SOURce Cn`
   - `WAV:WIDTh WORD` when the preamble reports more than 8 nominal bits; use `--wav-width byte` only for an explicitly labeled lossy historical comparison
   - `WAV:BYTeorder LSB` for WORD transfers, followed by `WAV:BYT?` readback
   - `WAV:INTerval 1`, then verify `WAV:INT?` is `1`
   - `WAV:STARt <start>`
   - `WAV:POINt <count>`
   - `WAV:DATA?`
8. Save one raw binary file and one metadata file per segment. For BYTE expect `count` payload bytes; for WORD expect `count * 2` payload bytes. Check each returned payload length and checksum. On the verified firmware, requests above 250,000 points were observed to return 250,000 points while `WAV:POIN?` echoed the request; this is not a universal limit, and the payload length is authoritative.
9. Build the full report only after all segments have contiguous ranges from `0` through `array_count - 1`.

For a trigger-following burst, configure the optional horizontal strategy before step 4:

```text
python3 scripts/capture_scope.py \
  --out /path/to/capture --channels C4 \
  --mode modern --capture-mode configured_capture \
  --prepare --trigger \
  --left-aligned-trigger --trigger-margin-div 1 \
  --memory-depth auto --reference-position 10 \
  --wav-width auto
```

This queries `TIM:SCAL?`, sets `TIM:DEL = (5 - margin_div) * timebase`, and verifies the timebase, delay, memory-depth, and optional `TIM:REF:POS` readbacks before `TRMD SINGLE`. With `margin_div=1`, the trigger has one division of pre-trigger context and nine divisions of post-trigger window. The strategy is opt-in and is not valid with `--existing-stopped`; use a larger margin when pre-trigger history is important.

Example for the current stopped C4 frame:

```text
python3 scripts/capture_scope.py \
  --host 192.168.10.2 --port 5025 \
  --out /path/to/c4-capture --channels C4 \
  --mode modern --capture-mode configured_capture \
  --existing-stopped --segment-points 5000000 \
  --probe-points 10000,1000000 \
  --wav-width auto
```

The command writes `C4/segment-*.bin`, response/prefix files, per-segment JSON, `C4/waveform.bin`, and `manifest.json`. It creates `waveform.bin` only after the complete range validates.

### Existing Immutable Stopped Frame

Use this only when the caller explicitly says the current stopped frame is the target.

1. Do not send `STOP`, `TRMD`, `RUN`, `ARM`, `WFSU`, or configuration writes.
2. Read `C1:WF? DAT2`, `C2:WF? DAT2`, `C3:WF? DAT2`, and `C4:WF? DAT2` as requested; save every raw response.
3. After all DAT2 reads finish, optionally issue `C<n>:WF? DESC` as a separate explicit diagnostic step.
4. Compare `array_count`/`data_length` from the descriptor with actual payload bytes. For 8-bit DAT2, bytes equal points.

### Configured Repetitive Capture

This is not immutable. It may use `WFSU SP,1,NP,0,FP,0` before the new `TRMD SINGLE` capture and may select a fresh waveform memory view. Label artifacts `configured_capture`, record every WFSU command, and do not use the result to make claims about the original stopped frame. Never send WFSU after `Stop` in a stopped-frame read.

## Binary Response Rules

Use `scripts/scope_protocol.py` for all byte parsing of **waveform** responses. `:PRINt?` is the documented exception and has its own bounded reader in `scripts/screenshot_capture.py`; see below.

- Search until `#` is found; arbitrary ASCII, NUL bytes, prompts, and status bytes may precede it.
- Read one ASCII digit `N`, then exactly `N` ASCII decimal length bytes, then exactly that many payload bytes.
- Validate the payload length. Keep `prefix`, the complete block header, payload, and SHA-256.
- A payload may contain `#`, NUL, CR, or LF; never split it on lines.
- A timeout, missing marker, non-decimal length, or short payload fails closed.
- **`:PRINt?` carries no IEEE 488.2 block header** on firmware `4.8.12.1.1.6.5`: it answers with a raw PNG stream closed by a single `LF`, so the rules above do not apply and `query_block()` legitimately fails with `invalid IEEE length-of-length`. Read bounded bytes until the `IEND` chunk plus that trailing `LF`, keep the SHA-256, and never `readline()` a screenshot. `scripts/screenshot_capture.py` is that reader: it validates the PNG signature, IHDR bounds and a legal bit-depth/colour-type pair, chunk order (IHDR first, contiguous `IDAT`, `PLTE` before `IDAT`, at most one `PLTE`, no unknown critical chunk), every chunk length and CRC, and the `IEND` plus one `LF` terminator under a total byte bound and a total elapsed-time bound. It keeps every received byte in the raw file even for a partial or invalid stream, refuses to replace an existing artifact, records a failed connect as JSON without creating a PNG, and passes the session timeout back on exit. `status`/`container_valid` describe PNG container structure only: no decoder runs, so `image_decode_status` is always `UNVERIFIED`, and an empty or random `IDAT` whose CRCs are correct still counts as a valid container while proving nothing about a viewable image or the frame it shows. The association with a downloaded waveform stays `UNVERIFIED`. Its framing is documented and offline-tested, not yet exercised against a physical instrument. See [Screenshot and waveform data](references/screenshot-and-waveform.md).

## Local AI Waveform Analysis

Use the bundled read-only analyzer after a capture has produced a complete `manifest.json`. It never reconnects to or writes the oscilloscope and it never replaces the raw `waveform.bin` evidence:

### Pre-analysis evidence gate

Complete this gate before any analyzer subcommand that produces a conclusion. It is the single authority for measurement provenance, channel identity, record completeness, analysis time, pulse-boundary semantics, threshold placement, and drive claims. `inspect` is the integrity entry, not analysis evidence.

- **Try to preserve the instrument's own readings first; their absence must not block offline analysis.** Record every existing readout verbatim with its item, source channel, threshold settings, measurement window, gating, and definition (what the value is computed over). Read that context instead of assuming it: `:MEASure:SIMPle:SOURce?` reports the channel whose value a readout describes, while `:MEASure:THReshold:SOURce?`, `:MEASure:THReshold:TYPE?` and `:MEASure:THReshold:PERCent?` or `:MEASure:THReshold:ABSolute?` report the threshold source that the following threshold queries address and its high/mid/low settings (documented, programming guide printed pp. 182-185). Record both sources separately and never assume they agree: when the measurement source and the queried threshold source differ, the measurement channel's own thresholds were not read, so its threshold levels stay `unknown` and any statistics comparison stays `UNVERIFIED`. Do not rewrite `:MEASure:THReshold:SOURce` to read another channel's levels — that changes instrument state. If a readout is unavailable — an unsafe or undocumented query, or no readout exists — record it as `unavailable` with the unknown metadata and continue with evidence-based offline analysis. Do not change the instrument configuration to make it queryable. A missing readout blocks only statistical-consistency claims and inferences beyond the offline evidence; it does not block a conclusion the captured samples support on their own.
- **Compare statistics only on identical measurement conditions.** An instrument readout and an analyzer statistic may be compared only when they come from the same capture, channel, measurement window, gating, threshold, and count definition. Classify each condition as matched, `unknown` (not recorded, not queryable, or not established), `not_exposed` (no control for it is exposed by the interfaces and documents this Skill records), or `not_applicable` (the quantity is not part of this measurement). `not_exposed` records only the scope of this Skill's records: it is not evidence that the instrument has no such control, so the measurement behaviour behind it stays `UNVERIFIED` unless the absence is independently established. `not_applicable` likewise describes the quantity, not a value. Neither classification turns a differing threshold, window, or count definition into agreement. Any `unknown` or differing condition keeps the comparison `UNVERIFIED` rather than reconciling the numbers; a whole-frame instrument statistic never describes a stage or anomaly, and no comparison substitutes for full-record analysis.
- **Keep the measurement window separate from the display window.** Record the display timebase state in effect when the reading was taken — `TIMebase:SCALe`, `TIMebase:DELay`, and `TIMebase:REFerence:POSition`, from the manifest `capture_configuration` snapshot for that setup — as display configuration, and record the range a readout actually evaluates as a separate item from evidence about that readout (`firmware-scoped`: on this target a zoom change moved a `:MEASure:SIMPle` value, so the zoomed window drove it — one observed case, not a documented rule). When the evaluated range is not established, record it `unknown`; do not infer it from the display timebase values, and do not default it equal to the display window. The display state is also not proof of measurement gating: the only gating control this Skill records is `:FUNCtion<x>:INTegrate:GATE` (math integrate), so basic-measurement gating is `not_exposed` only in the sense that the recorded interfaces and documents expose none — the measurement's own gating behaviour stays `UNVERIFIED`. Compare a reading with a sub-range analyzer statistic only when the analyzer range equals the recorded evaluation range.
- **Resolve the channel map before attributing a signal name.** The **Hardware Profile** mapping above is one verified bench setup, not a default. `capture_scope.py` records `channel_mapping` only from `--channel-mapping`, together with `channel_mapping_source` (`user-supplied`, otherwise `unknown`); the scope exposes no channel-name readback, so no tool output can confirm wiring. A manifest from an earlier capture script instead carries the fixed template `{"C1": "ENABLE", "C2": "nFAULT", "C3": "HOC", "C4": "P4.1/CMP"}`: treat that exact constant as an unverified template carrying no per-capture wiring evidence, not as the capture's declaration. Compare whatever the caller states with the wiring, probe, and user-supplied channel description, and never relabel a channel so the data fits an expected signal.
- **An unresolved signal name blocks attribution, not analysis.** When no channel mapping is confirmed, analyse the physical channel (`C2`) and report its signal name `UNVERIFIED`; physical-channel conclusions, including statistics compared on that same physical channel, stand on the captured samples. A functional or protocol claim ("this is nFAULT", "this is the HOC drive", "this frame proves reception") requires the resolved identity, and only those claims are blocked. Stop and report the analysis `UNVERIFIED` only when the `inspect` integrity record itself is missing or not `COMPLETE`.
- **Open the complete descriptor record through the manifest.** Run `python3 scripts/analyze_waveform.py inspect --capture <capture-dir> --channel <Cn>` and require `integrity.status = COMPLETE`, `capture.points` matching the WAVEDESC waveform point count, and `integrity.segments_verified` matching the manifest's segment count. `ACQ:POIN?` reports screen waveform points (manual printed p. 21); modern captures mark `scope_record.semantics = screen` and report that quantity separately. Payload completeness proves coverage of the descriptor record, not the whole acquisition memory or its correspondence to the screen. Read `screen_range` and `time_correspondence` and state their unresolved conditions. Older `INCOMPLETE` modern manifests may be checked with explicit `--revalidate-screen-range`: only recorded screen-count/duration comparison failures can be reclassified, all file and segment checks still run, and the derived output retains the source manifest hash and original failure reasons without changing raw artifacts. Unknown failure reasons remain a refusal. Never glob `*.bin` or treat a single segment as the record; use the manifest's merged `waveform.bin`.
- **Use descriptor time and CLI time windows.** Take time from `sampling.origin_s` and `sampling.interval_s`, and pass ranges as `--start-time/--end-time`. These are descriptor-reported coordinates; screen, trigger and decoder alignment remain `UNVERIFIED` until independently established. The modern time formula follows manual printed pp. 391-392 and 454; retain it rather than compensating a measured offset with a fixed constant. Do not derive time from filenames or a guessed sample rate, or treat a segment-local index as a record index.
- **A rising edge is not a complete positive pulse.** Report pulses touching a scan or capture boundary separately as boundary/`INCOMPLETE` items, never padded or dropped. Read the pulse fields together: `pulses.count` is every pulse the scan produced, `pulses.complete_count` counts those with both edges inside the record, `pulses.incomplete_count` counts the boundary ones, and `pulses.status` is `COMPLETE` or `COMPLETE_WITH_INCOMPLETE_BOUNDARY_PULSES`. Compare `PPULSES` or `NPULSES` only after confirming what the instrument counts: the manual defines them as the positive or negative pulse count in the screen waveform without stating how a pulse cut by the screen edge is treated. Neither `complete_count` nor `count` is automatically equivalent to that reading. Match the evaluated window and boundary rule before claiming agreement; otherwise report the separate counts and keep equivalence `UNVERIFIED`.
- **Hysteresis thresholds must sit outside the noise band**, derived as in step 1 of the mandatory gate below. A local minimum or maximum is not a crossing and does not prove activity: activity requires recorded threshold crossings on original-resolution samples under the stated thresholds.
- **A low MISO level is not proof of active drive or protocol reception.** It shows only the sampled level of that line. A received-frame claim needs an actual frame decode plus its protocol context; an active-drive claim needs independent electrical evidence. A decode does not prove drive, and a level reading does not prove reception.

The gate is complete when every recorded readout carries its status (`preserved` or `unavailable` with the unknown metadata) and its source, threshold, and window context — display configuration and evaluation range recorded separately, each `unknown` when not established; the channel map is recorded with its source (`user-supplied` or `unknown`); the `inspect` integrity confirmation is recorded; and every unresolved condition is named. A missing readout leaves statistical consistency `UNVERIFIED` and does not stop offline analysis; an unresolved signal name leaves attribution `UNVERIFIED` and does not stop physical-channel analysis.

### Mandatory analysis gate

Evidence labels in this section are `firmware-scoped`: SDS824X HD, firmware `4.8.12.1.1.6.5`, SCPI TCP `5025`.

Before making any conclusion about periodic-signal presence/absence, drive, frequency stability/change, duty/pulse timing, or a long record's phases, the agent must:

0. **Run the verdict pre-screen first, as one command.** After the pre-analysis gate above has confirmed the record through `inspect`, `python3 scripts/analyze_waveform.py verdict --capture <capture-dir> --channel <Cn>` is the first conclusion subcommand, before any other analyzer subcommand. The conclusion must quote `claims.can_claim`, must not assert anything in `claims.cannot_claim`, and must reproduce every `claims.must_state` entry verbatim. A `REFUSED` verdict is a complete answer and must be reported as such, never worked around with hand-rolled arithmetic. Steps 1-5 are the escalation path when the verdict is `OBSERVED` but the task needs stage, transition, or anomaly detail that a pre-screen cannot give.
1. **Prove the thresholds are placed on the signal's own levels, not on its noise.** The analyzer only reports whether a threshold was *reached*, never whether it was *reached in the right place*: a threshold sitting inside the noise band returns a perfectly healthy `OBSERVED` / `low_duty_pulse_train` result whose silent prefix, first-edge time and pulse count are all wrong, with no field flagging it. Derive the levels first from `summarize.summary.percentiles_v` (calibrated) or `percentiles_code` (code domain — the two are mutually exclusive: a `VALID` calibration emits only the `_v` family plus `underlying_code_statistics`, which carries min/max but no percentiles). Place `high` under the code where p95 and p99 coincide and `low` above p50; for a bipolar or multi-level record take the boundary codes from a deliberately low `structure` pass and read `edges.items[].before_code` / `after_code`. `summarize` accepts no time range, so a whole-record percentile describes the whole record only — reproduce any single-region claim with a sub-range `structure` pass. `firmware-scoped` failure: on a 5 s record whose first 0.45 s sat at a 0.02–0.4 V noise floor, thresholds of 0.13/0.39 V moved the first edge from 0.0962 s to -0.4141 s (silent prefix 0.086 s instead of 0.596 s), added 67 spurious crossings, and still reported `status = OBSERVED`. State the evidence for each threshold pair you use.
2. Run `structure` on the **full record** at original resolution with explicit hysteresis thresholds. Inspect `coverage.full_record_scanned`, `edges.items_complete`, `pulses.items_complete`, and `evidence.observation_status`. If any is incomplete, truncated, `UNVERIFIED`, or limited to a time subrange, state the limitation and do not make a record-wide claim.
3. If the structure contains at least two complete cycles or the task asks whether a periodic regime changed, run `regimes` on the **same full record, channel, thresholds, and calibration context**. Inspect `data_integrity_status`, `segmentation_status`, `overall_status`, `coverage.count_reconciliation.reconciles`, regime/transition/cycle counts, unresolved phases, anomalies, and each returned item's completeness flags before drawing conclusions.
4. Reconcile each claim with the returned per-cycle values and edge/pulse references. Report every regime and every unresolved candidate phase, including brief phases; do not summarize away a detected stage or anomaly. Use `window` only to inspect samples around referenced transitions/anomalies, never as a replacement for full-record structure.
5. **Re-scan at a second threshold pair whenever the pulse table shows paired or equal-width pulses** — that is the signature of one real pulse being cut into several segments by an intermediate level. `pulse_clusters` cannot reveal this: grouping is by low-level gap only, so a split pulse stays one cluster and `cluster_count` is a correct computation, just not a description of the sub-structure. `firmware-scoped` example: one 136.25 ms gate cycle held a 45.2 ms high, a 0.2 ms notch, a 0.03 ms spike and another 45.2 ms high, so a single threshold reported `continuous_carrier`, `cluster_count=1`, 133 pulses, and nothing marked the split. Report the levels separately instead of claiming one pulse count.

If the waveform is not periodic/pulse-like, explicitly mark regime segmentation as not applicable and state which structure evidence supports that choice. If cycle support is insufficient, or any output is truncated/prefix-only, report the stage analysis as unresolved/`UNVERIFIED`; do not silently skip the regime pass and do not convert missing evidence into a negative claim. `inspect`, `summarize`, a screenshot, `events` pagination, and an M4/stride preview alone do not satisfy this gate.

Two fields mean "you are not looking at the whole record": `status=UNVERIFIED` with `edges.count_is_lower_bound=true` (the edge budget stopped the scan) and `truncated=true` with `items_complete=false` (the JSON budget kept a prefix). `classification` and `pulse_clusters.count` are computed **before** truncation and stay authoritative, but any later statistic over `edges.items` / `pulses.items` is prefix-only. Check `count` against `returned` before reusing either list.

python3 scripts/analyze_waveform.py summarize --capture /path/to/capture --channel C4 --preview-buckets 256
python3 scripts/analyze_waveform.py events --capture /path/to/capture --channel C4 --threshold-codes 20 35 --limit 100
python3 scripts/analyze_waveform.py window --capture /path/to/capture --channel C4 --start 123456 --count 512

python3 scripts/analyze_waveform.py structure --capture /path/to/capture --channel C4 --threshold-volts 0.8 2.0 --cluster-gap-s 0.002 --max-edges 20000
python3 scripts/analyze_waveform.py regimes --capture /path/to/capture --channel C4 --threshold-codes 20 35 --measures auto --min-cycles-per-side 5

The analyzer validates the complete frame, merged file size, SHA-256, segment ranges, actual payload point counts, width, byte order, and sampling metadata before reading samples through NumPy `memmap`. It scans large records in bounded chunks and returns compact JSON rather than raw arrays. `summarize` reports exact integer-code statistics and an M4 preview labeled `visualization_only_lossy`; the preview must not be used as a substitute for event detection. To detect narrow pulses, scan the full record or use original-resolution extrema/event detection; do not use one-point or mean sampling as evidence that a signal is absent. `events` scans original-resolution samples and returns bounded pages with a stateless cursor; `--start-time/--end-time` limits the scan to a relative display-time range. `window` is the escalation path for inspecting samples around an event and accepts either sample indices or a half-open time range. `ringing` analyzes one bounded local window and reports heuristic edge overshoot, undershoot, residual crossings, frequency, and decay when enough evidence exists. It does not return a full local array, so call `window` separately when the AI needs the raw samples.

`structure` is the raw-edge fact layer: it scans every original sample (`evidence.raw_scan = true`, `evidence.stride_used = 1`) and returns the ordered edge table - event id, direction, sample, time, before/after codes, same-direction interval, and time uncertainty - rather than a paged view.

A clean-looking `status = OBSERVED` does **not** mean the thresholds were placed correctly; see gate step 1 for the placement evidence each threshold pair needs. No output field evaluates whether the chosen levels belong to the signal or to its noise.

A pulse table with **paired or equal-width pulses** (for example two 45.2 ms pulses separated by a 0.2 ms notch and a 0.03 ms spike) means one physical pulse is being cut by an intermediate level the thresholds do not represent; re-scan at the intermediate level rather than reporting the split count. `pulse_clusters` groups by low-level gap only, so it stays silent about this split.

`regimes` is a second analysis layer that derives complete cycle measurements from this raw structure and groups sustained changes into stages; it does not replace the edge table or the original capture. Rising and falling edges are paired in raw order into `pulses` with start/end sample and time, width, code levels, thresholds, boundary flags, and `status`; a high interval without a matching edge inside the scanned range is `INCOMPLETE` and is never padded. Pulses are grouped into `pulse_clusters` by a low-level gap that defaults to three times the observed median pulse period (or eight sample intervals when no period evidence exists) unless `--cluster-gap-s` is given; there is no fixed millisecond window. The result is labelled `continuous_carrier`, `short_burst`, `low_duty_pulse_train`, `pulse_train`, `single_pulse`, `no_crossing_observed`, or `insufficient_evidence`, and every label carries `classification.basis`, `classification.metrics`, and `classification.evidence` (edge ids, pulse ids, sample range) so it can be re-derived from raw samples.

`structure` fails closed on volume. `--max-edges` is a hard edge budget: when it is exceeded the response is `classification.status = UNVERIFIED` with `edges.count_is_lower_bound = true`, `edges.lower_bound`, `pulses.status = UNVERIFIED`, and `full_record_scanned = false`, never a silently truncated table presented as complete. JSON bounding is a separate, also explicit limit: when `--max-json-bytes` shortens `edges.items`, `pulses.items`, or `pulse_clusters.items`, the section keeps its authoritative `count` and reports `items_truncated = true`, `items_complete = false`, and the `json_output_truncated_items_are_prefixes` limitation.

`firmware-scoped` operational limit: `--max-json-bytes` is capped at 4 MiB, and the bounding loop re-serializes the whole document for every item it removes. A 25 M-point, 5 s record containing a 19.92 kHz pulse train (about 20 000 pulses / 39 000 edges) did not finish a single full-record `structure` call in 25 minutes, and `regimes` on the same record behaved the same way. Cover such a record with **contiguous sub-range windows that each fit under the budget** (`--max-json-bytes 4194304`; 0.2 s windows over 5 s took about 12 s in total, each window `truncated=false` with `edge_scan_complete=true`), then reconcile the windows. Report the result as contiguous windowed coverage of the full record, quote the window boundaries, and never present a single sub-range scan as a full-record result. A window holding only one complete cycle legitimately returns `regimes` `UNSUPPORTED`; take that stage's regime evidence from a window with enough complete cycles and state which window it came from.

`regimes` autonomously considers supported per-cycle measurements by default (`--measures auto`), or accepts an explicit list such as `period_s,duty_cycle,high_width_s`. It can identify sustained period/frequency or pulse-shape changes, summarize each stage and flag isolated cycles as anomalies. The default transition rule needs at least five complete cycles on each side; shorter candidate stages and uncertain boundaries remain unresolved rather than being asserted as stable stages. Smooth monotonic drift is reported as trend evidence within a regime, not forced into step changes. Output separates `data_integrity_status` from `segmentation_status`; an intact capture with uncertain interpretation is not a corrupt/incomplete waveform. When `--max-edges`, `--max-cycles`, or JSON output limits are exceeded, inspect `overall_status`, `coverage`, and each section's `items_complete`/`items_truncated` before relying on the report.

The M4 preview from `summarize` and any local `[::stride]` decimation are visualization only. Never derive an absence, no-drive, or duration conclusion from an aggregate, a window count, a mean, a preview, or a decimated view; use `structure` (or `events` plus `window`) on original-resolution samples. A negative statement must state the detection capability behind it: `evidence.observation_status = NOT_OBSERVED_WITHIN_DETECTION_CAPABILITY` together with `evidence.detection_resolution_s` and `evidence.minimum_detectable_pulse_s`. Features narrower than one sample interval between the two thresholds can be missed, so "no crossing observed" is not "no drive".

All analysis times are relative to the waveform display origin reported in `sampling.origin_s`, not wall-clock time. The time range is half-open: `[start-time, end-time)`. Do not combine time arguments with sample-index arguments. `ringing` marks windows touching the capture boundary, edges without enough pre-context, and ring-down that remains above noise at the window end; those flags prevent a local estimate from being mistaken for proof that the physical event ended.

WORD captures retain raw signed little-endian codes. Unless an independent calibration JSON is supplied, WORD analysis reports `OBSERVED_UNVERIFIED` and emits code-domain values only; a 16-bit transport container is not automatically treated as a 16-bit voltage-calibrated ADC result. That refusal is justified and must not be bypassed by arithmetic on the descriptor: the observed descriptor `code_per_div=30` with `vdiv_with_probe=2 V/div` implies 0.0667 V/code (15 codes/V), while the same frame's own `:MEASure:SIMPle:VALue? PKPK` gives **3840 codes/V** - a factor of 256. A usable calibration can still be derived without any screenshot by dividing each channel's raw code span by the scope's PKPK reading for that channel; four channels agreed to four significant digits (C1 5.23333 V, C2 3.49583 V, C3 5.51667 V, C4 5.75417 V against raw spans giving 3840 codes/V on every channel). Write that into the calibration JSON shape below and the analyzer reports `status = VALID`, enabling `--threshold-volts`. BYTE voltage conversion takes V/div from the captured panel snapshot `C<n>:VDIV?` (probe factor already applied by the panel), falling back to descriptor VDIV only when no snapshot exists; a parsed snapshot that disagrees with the descriptor wins, and the override is recorded as `panel_snapshot_vdiv_overrides_descriptor`. A mismatch is still reported as a calibration limitation rather than silently used to produce voltage fields, and an unparseable snapshot reply is a failed cross-check (`capture_snapshot_vdiv_unparseable`), never a skipped one. An observer/probe at the same frequency as the measured signal can alias into a false state change; use an unrelated observation rate or a discriminating comparator output. Interpret counter hypotheses only when they explain all observations, including periodic retry windows. The instrument's own whole-frame simple measurements are a magnitude check only: on a record that spent most of its length at 19.92 kHz, the whole-frame `FREQ` reported 7.3433 Hz, `PWID` reported the stage-1 45.4248 ms, and `DUTY` reported 33.357 %, so a whole-frame reading must never be used as the stage description. Analysis output defaults to stdout and must be written outside the raw capture directory with `--out`.

An independent WORD calibration file must bind evidence to the exact merged waveform SHA-256 and use this minimum shape:

```json
{
  "channels": {
    "C4": {
      "word_scale_verified": true,
      "capture_sha256": "<merged waveform SHA-256>",
      "word_codes_per_div": 19200,
      "vdiv_v_per_div": 5.0,
      "offset_v": 0.0,
      "evidence": "known DC reference and BYTE/WORD comparison"
    }
  }
}
```

The analyzer computes `code_scale_v = vdiv_v_per_div / word_codes_per_div`, so the two fields are only meaningful **together**: `word_codes_per_div` is codes per division *at that same panel V/div*, never codes per volt. The firmware-verified frame above ran C4 at `2 V/div` and produced `7680` codes/division, i.e. 3840 codes/V; the 5 V/div example therefore carries `3840 * 5 = 19200`, not `7680`. Copying the 7680 from a 2 V/div frame into a 5 V/div entry scales every resulting voltage by 2.5 and still reports `status = VALID` — the loader validates the hash, the boolean, the sign and a non-empty evidence string, but never cross-checks the two numbers against the frame's own span. Either supply `vdiv_v_per_div` equal to the panel setting of the frame being calibrated, or verify `word_codes_per_div / vdiv_v_per_div` against `(max_code - min_code) / PKPK` from the same frame.

The analyzer rejects stale or incomplete evidence back to code-domain output. It does not infer WORD voltage scaling from `code_per_div * 256` alone.

Deriving the scale from the frame's own `:MEASure:SIMPle:VALue? PKPK` is an **internal consistency check, not an independent voltage calibration**: both numbers come from the same instrument and the same acquisition. It is sufficient to place thresholds correctly and to reproduce the instrument's own readings, and it must be labelled that way (`OBSERVED_UNVERIFIED` for absolute accuracy). An independently verified scale needs a traceable reference such as a known DC source.

## Waveform Decode and Validation

For modern `WAVeform:PREamble?`, parse the documented little-endian fields in `scripts/scope_protocol.py`. Keep at least `wave_array_1`, `wave_array_count`, `start`, `interval`, `vdiv`, `offset`, `code_per_div`, `adc_bit`, `sample_interval`, `delay`, `tdiv`, and `probe`.

For BYTE data, decode signed samples as `byte - 256 if byte > 127 else byte`; `raw - 128` is a half-scale offset, not a two's-complement decode, and it shifts the zero point by 128 codes. Take the V/div from the panel snapshot `C<n>:VDIV?`, not from the legacy descriptor: on firmware `4.8.12.1.1.5` the descriptor reported `vdiv=0.2`/`probe=10` on all four channels (a flat `2 V/div`) while the panel ran `5/2/2/1 V/div`, so the descriptor reproduces only the channels that happened to be at 2 V/div and scales C1 by 2.5 and C4 by 2. A `valid` calibration therefore requires a parsed panel snapshot; an unparseable or missing reply is reported as `capture_snapshot_vdiv_unparseable` and drops the result to code domain rather than skipping the check. Do not hard-code `/32`; the observed `code_per_div` is `30`. For WORD data, retain the raw two-byte LSB payload and report `voltage_decode=unverified_for_WORD` until the device-specific left-alignment ratio is independently calibrated. A 16-bit transport container must not be called a 16-bit ADC result. The current observed descriptor reports `nominal_bits=16`, `code_per_div=30`, and `MAX_VALUE=7680`; the WORD transfer has been hardware-verified for byte completeness, not voltage scaling.

BYTE transfer has two limits that must be stated whenever BYTE voltages are quoted. Its representable span is only `±127 codes / 30 = ±4.23 divisions`, so a 10-division screen is truncated to the middle 4.23 divisions above and below the offset; on a 1 V/div channel a steady `+4.27 V` (`4.27 divisions`) is clipped to code `127` and arrives as `+4.23 V` with zero variance, and no post-processing recovers it — re-read that channel as WORD or lower V/div. Its quantization is `1 LSB = V/div ÷ 30` (`74 mV` at 2 V/div, `167 mV` at 5 V/div), so a record spending its time near the noise floor may occupy only a few dozen codes and carry 2-5 % amplitude uncertainty. WORD is 256× finer (`7680` codes/div, `3840` codes/V at 2 V/div): use it for any threshold decision.

`start` is a sample index into the whole record, not zero. Add it to the reported origin (`horizontal_offset - timebase_s * 5 + start * sample_interval`); a slice that begins at record sample `15 000 000` of a 20 M-point record otherwise reports every event 1.5 s early while the capture still counts as `COMPLETE`.

Report the screen point count, WAVEDESC record point count, and actual downloaded point/byte counts separately. Modern `frame_report.status` describes descriptor/download payload integrity; `screen_range.status` and `time_correspondence.status` describe separate correspondence evidence. A download shorter than its descriptor is `INCOMPLETE` even when it covers the screen. Different screen and descriptor counts alone do not prove a short download. See [Programming notes](references/programming-guide.md#record-ranges-and-time-coordinates) for the documented definitions and explicit offline revalidation.

Any empty, truncated, wrong-width, overlapping, or missing segment invalidates the complete channel. Do not infer missing samples or silently pad.
